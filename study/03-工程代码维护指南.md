# 从0开始维护当前工程代码

本文档介绍如何维护 OpenClaw 工程代码，包含代码规范、提交流程、依赖管理、发布等方面的内容。

## 前置阅读

在开始维护代码之前，请先阅读：
- `CLAUDE.md` - 项目整体指南和规范（非常重要，必须阅读）
- `CHANGELOG.md` - 版本变更历史
- `.github/CONTRIBUTING.md` - 贡献指南

## 代码风格规范

### 语言和类型

- 使用 **TypeScript (ESM)** 开发
- 优先使用严格类型，避免 `any`
- 禁止添加 `@ts-nocheck`，遇到类型问题尽量修复根因

### 格式化和 lint

项目使用 Oxlint 和 Oxfmt 进行格式化和 lint 检查：

```bash
# 检查代码格式和 lint
pnpm check

# 自动修复格式问题
pnpm format:fix
```

**在提交代码之前必须运行：**
```bash
pnpm check
```

### 文件大小规范

- 目标：保持文件在 ~700 LOC 以下
- 如果文件过大，提取帮助函数，拆分文件
- 避免创建 "V2" 拷贝，重构原有文件

### 命名规范

- 产品/文档标题：**OpenClaw** (大写 O 和 C)
- CLI命令/包/路径/配置：**openclaw** (全小写)
- 变量/函数：遵循 TypeScript 驼峰命名
- 使用美式拼写（`color` 而非 `colour`，`behavior` 而非 `behaviour`）

### 注释规范

- 对于复杂/不明显的逻辑，添加简要注释
- 自解释的代码不需要注释

## Git 工作流

### 分支规范

- `main` - 主开发分支，来自官方 upstream
- 功能开发：基于 `main` 创建功能分支，命名格式 `feat-xxx` 或 `fix-xxx`

### 提交规范

使用 Conventional Commit 格式：

```
type: 简短的描述

详细说明（可选）
```

**type 常用值：**
- `feat`: 新功能
- `fix`: 修复bug
- `docs`: 文档修改
- `refactor`: 重构
- `chore`: 构建/工具相关
- `test`: 测试相关

示例：
```
feat: 添加新的XXX命令
fix: 修复XXX在YYY情况下的崩溃问题
docs: 更新安装说明
```

### 提交前检查

提交代码之前：

```bash
# 检查格式和lint
pnpm check

# 如果有格式问题自动修复
pnpm format:fix

# 运行相关测试
pnpm test path/to/test-file.test.ts
```

### 同步官方最新代码

项目使用 upstream 跟踪官方仓库：

```bash
# 获取最新官方代码
git fetch upstream

# 合并到当前main分支
git checkout main
git merge upstream/main

# 推送到自己的远程
git push origin main
```

建议定期同步官方更新，避免合并冲突过大。

## 依赖管理

### 基本原则

- 核心依赖放在根目录的 `package.json`
- 插件/扩展的依赖放在插件自己的 `package.json`
- `openclaw` 在插件中放在 `devDependencies` 或 `peerDependencies`，不要放在 `dependencies`（避免重复安装）

### 添加新依赖

```bash
# 添加生产依赖
pnpm add package-name

# 添加开发依赖
pnpm add -D package-name
```

### 依赖注意事项

- 不要更新 Carbon 依赖（项目约束）
- 任何带有 `pnpm.patchedDependencies` 的依赖必须使用精确版本（不能有 `^` `~`）
- 修补依赖需要明确批准，默认不做

### 更新依赖

```bash
# 更新指定依赖
pnpm update package-name

# 更新所有依赖
pnpm update
```

## 测试

### 运行测试

```bash
# 运行所有测试
pnpm test

# 运行单个测试文件
pnpm test path/to/file.test.ts

# 运行单个测试文件带监听模式
pnpm test path/to/file.test.ts --watch

# 生成覆盖率报告
pnpm test:coverage
```

### 测试覆盖率要求

框架要求：
- 行覆盖率 70%+
- 分支覆盖率 70%+
- 函数覆盖率 70%+
- 语句覆盖率 70%+

### 编写测试

- 测试文件命名：`*.test.ts`
- e2e 测试：`*.e2e.test.ts`
- 和源文件放在同一目录

## 代码重构指南

### 动态导入规范

- 不要混合 `await import("x")` 和静态 `import ... from "x"`
- 如果需要懒加载，创建 `*.runtime.ts` 边界文件，从那里重新导出
- 重构后运行 `pnpm build`，检查是否有 `[INEFFECTIVE_DYNAMIC_IMPORT]` 警告

### 类继承和组合

- 不要使用原型变异共享行为（`applyPrototypeMixins` 等）
- 使用显式继承 `A extends B extends C` 或帮助函数组合
- 保持 TypeScript 可以正常类型检查

## 版本发布

### 版本号位置

修改版本号需要更新以下位置：

- `package.json` - CLI版本
- `apps/android/app/build.gradle.kts` - `versionName`/`versionCode`
- `apps/ios/Sources/Info.plist` - `CFBundleShortVersionString`/`CFBundleVersion`
- `apps/ios/Tests/Info.plist` - 同上
- `apps/macos/Sources/OpenClaw/Resources/Info.plist` - 同上
- `docs/install/updating.md` - 固定npm版本
- `docs/platforms/mac/release.md` - APP_VERSION/APP_BUILD 示例

> `appcast.xml` 只在发布 Sparkle 新版本时修改。

### 发布前检查

```bash
# 运行发布前检查
node --import tsx scripts/release-check.ts
pnpm release:check

# 运行安装冒烟测试
pnpm test:install:smoke
```

### 更新 CHANGELOG

在 `CHANGELOG.md` 中添加新版本条目：

```markdown
## vYYYY.M.D - 日期

### Changes
- 新功能1
- 新功能2

### Fixes
- 修复问题1
- 修复问题2
```

- 只保留用户可见的变更
- 不要包含内部修改
- `Changes` 在前，`Fixes` 在后

### 打标签和发布

```bash
# 提交版本更新
git add .
git commit -m "bump version to vYYYY.M.D"

# 打标签
git tag vYYYY.M.D

# 推送
git push origin main --tags
```

## 合并 Pull Request 指南

在合并 bug 修复 PR 之前，必须满足：

1. 有症状证据（复现步骤/log/失败测试）
2. 验证了根因，指出文件和行号
3. 修改触及了相关代码路径
4. 增加了回归测试（可行情况下）

不满足条件不要合并。

## 故障处理

### Rebase 冲突

解决冲突后：

```bash
# 继续rebase
git rebase --continue

# 或者放弃
git rebase --abort
```

### 本地工作区脏了需要拉取

```bash
# 保存当前修改
git stash

# 拉取
git pull

# 恢复修改
git stash pop
```

## 预提交钩子

项目使用 prek 运行预提交钩子，和 CI 检查相同：

```bash
# 安装预提交钩子
prek install
```

安装后每次提交会自动运行检查。
